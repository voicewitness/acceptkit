# 架构

## 0. 目标与读者

这份文档写给要改 acceptkit 内核、或要给自己的项目写扩展包的人，回答三件事：acceptkit 分几层、各层管什么；项目数据存在哪、为什么这么存；私有能力从哪里接进来。

这三件事都服务于同一个产品目标（见 [product.md](product.md)）：让编码 agent 做的验收，结论能信、能复核。架构上的落法是：判定交给不调模型的工具层按规则做、原文落盘，闸门由工具强制，状态全部落进存储 —— 不靠执行验收的 agent 自觉，也不靠对话记忆。下面每一节是这条思路在某一层的做法。

## 1. 三层

acceptkit 分入口、工具层、存储三层：入口一期是 Skill、二期加内置 Agent，工具层是不调模型的 CLI，存储是项目目录加 SQLite；管理页面读同一份存储。

| 层 | 是什么 | 要点 |
|---|---|---|
| 入口 | 一期：Skill，宿主编码 agent 读 SKILL.md、调用 CLI；二期：内置 Agent，产品自带对话循环、调用模型 API | 两者共用同一份验收手册（`skill/` 下的文档） |
| 工具层 | acceptkit CLI：用例、运行、记录、观测、复核、报告、评审单、回归轮、闸门、设备租约、知识、环境、索引 | 不调模型 |
| 存储 | 项目目录（文件）+ SQLite（租约、审批、环境快照、索引） | 见第 3 节 |
| 管理页面 | `acceptkit serve`：本机网站，项目列表 + 各项目看板 | 读同一份存储；页面上的批准、裁定、答复经 CLI 写回，见第 8 节 |

- 工具层**不调用任何模型**。判定由观测规格 + 谓词完成，结论原文落盘。
- 闸门（白名单、危险动作确认、评审单批准、卸载审批）在工具层强制执行，不依赖 agent 遵守提示词。
- 所有状态写进存储，不留在对话里。换入口、换会话都能接着做。

## 2. 目录

代码仓库和项目数据分开放：acceptkit 是开源的，工具里不能带任何一个人、一个组织的环境（见 000-philosophy.md「分清谁的东西」），项目的用例、知识、证据只能放在仓库外。仓库的目录：

```
acceptkit/
  bin/acceptkit.mjs      CLI 入口
  core/                  引擎：用例模型、运行、证据闸、评审单、回归轮、版本范围、平台适用性、报告、看板
  core/project.mjs       找项目、读配置、加载 pack.mjs
  core/knowledge.mjs     知识（Markdown + 标签）；core/secrets.mjs：#secret 遮蔽
  core/phase1.mjs        sut / import / select
  core/case-quality.mjs  用例质量标准：规则、存量基线、豁免（见 case-quality.md）
  core/hosts.mjs         被测 App（宿主）登记：一个项目多个 App 时，这一步用哪个 App
  core/settings.mjs      设置：流程各步要用的设置项（构建、驱动），按宿主 / 平台的固定路径读写、借鉴与执行
  core/ops.mjs           操作库：读写、校验、旧写法迁移；推测的配方不执行
  core/config-edit.mjs   项目配置的写口：每个键登记类型，写入与 doctor 按它校验
  core/server.mjs        管理页面（acceptkit serve）：项目列表、各项目看板、按需出图
  core/links.mjs         报告链接：按上下文定位到看板面板
  core/store/            SQLite 访问（node:sqlite）
  adapters/              内置载体：android（adb）、web（CDP，独立浏览器实例）、ocr（截图文字识别）；iOS 模拟器（simctl）直接在 core 里调
  skill/                 通用 SKILL.md 与验收手册
  examples/web-demo/     公开示例项目（零私有扩展可跑通）
  scripts/               检查脚本（泄漏扫描等）
  test/                  测试
```

项目数据**不在仓库里**。一个「项目」是一个目录：

```
<project>/
  acceptkit.project.json   项目配置：名称、扩展包、闸门白名单、被测 App（hosts）
  pack.mjs                 （可选）扩展钩子：私有观测器、目标解析、领域命令
  knowledge/               知识：Markdown，可带标签（测试账号不在这里，见第 6 节）
  cases/                   用例（JSON，人可读）
  runs/<run>/              运行：result.json、证据、截图、报告
  state/                   评审单、回归轮、复核包、阻塞台账……
  .acceptkit/acceptkit.db  SQLite：设备租约、审批记录、环境快照、索引
```

CLI 找项目的顺序：命令行显式指定 → 环境变量 → 从当前目录向上找项目配置文件 → 用户配置里的默认项目。各自的名字见文末「附：命令与代码位置」。

## 3. 存储

存储的规矩是每类数据只有一份正本：人要直接读、要 diff 的放文件，只由 CLI 写、要事务的放 SQLite，索引从文件派生。逐类如下：

| 实体 | 正本 | 原因 |
|---|---|---|
| 用例、运行结果、评审单、回归轮、阻塞台账 | 文件（JSON） | 人可读、可 diff；项目自带的脚本可能直接读写这些文件 |
| 设备租约、审批记录、环境快照 | SQLite | 只由 CLI 写，需要事务，避免并发读改写竞争 |
| 用例 / 运行 / 结论索引 | SQLite（派生，可重建） | `acceptkit index` 按文件哈希增量重建；`acceptkit query` 用 SQL 管理大量用例 |
| 证据（截图、日志、抓包） | 文件 | 产物；路径记在 `runs/<run>/result.json`，复核时算哈希写回同一文件；库里只有每条结论的证据条数 |
| 知识 | Markdown 文件 | 用户可以直接编辑 |

索引是**派生数据**：每个实体只有一条写入路径（文件），索引任何时候都能从文件重建，不存在双写。当项目里直接读写文件的脚本都迁移为调用 CLI 后，该实体再切换为 SQLite 正本、文件降为导入导出格式。目前还没有实体切换过：上表文件正本的几类都还是文件，切换排在二期（见第 11 节）。

## 4. 扩展模型

内核零领域知识，项目的私有能力通过扩展包导出钩子接进来，内置能力走同一套钩子。这么分的原因同第 2 节：私有的观测器、领域命令属于项目，不能进开源内核；内置能力走同一套钩子，所以项目实现了某个钩子，就替换掉内置的那一项（下表「缺失时」一列就是内置的做法）。下表每个钩子都是可选的：不实现就按「缺失时」一列走，最小的扩展只导出观测执行器（公开示例项目里有一份）：

| 钩子 | 作用 | 缺失时 |
|---|---|---|
| `observers` / `observerStrength` | 观测执行器：`recipe.exec` → 函数，及其证据强度 | 断言按 fallback 降级；都不可用时记阻塞（「缺少观测扩展 <名字>」） |
| `resolvePort(recipe, udid)` / `appPortForPid(pid, udid)` | 找到被测 App 的调试端口 | 依次用 `ACCEPTKIT_APP_PORT`、配方里的 `port`、宿主配置 `hosts.<宿主>.ios.port` |
| `appPid(udid, bundle)` / `simState(udid)` | 模拟器上被测 App 的进程与状态 | 按 bundle 在 launchctl 列表里找；报模拟器开关机、设备名、是否安装（路径、版本）、是否在跑（pid） |
| `listDevices(platform)` / `bootDevice(ref)` | 选设备时「实际连着哪些」（身份列表）与「启动这一台」（返回 `{ ok, address }` 或 `{ ok:false, how }`）：自家设备池、测试里注入设备快照 | Android 读 adb、用 emulator 启动；iOS 读 `simctl list devices booted`、用 `simctl boot` 启动 |
| `uiHierarchy(port)` | 解析驱动工具的 UI 层级产物（含可见性），命令来自驱动设置的 `ui-tree` 动作 | 直接用 `ui-tree` 输出的文本行，命中即算遮蔽；没有设置则记为「无法确认」 |
| `obscurers` | 项目特有的遮蔽层（追加在内置的系统弹窗 / 隐私页 / Loading 之后） | 只查内置的几类 |
| `webObscuring(page)` | Web 截图前的遮蔽层检查 | 查页面上可见的对话框 |
| `ocr(png)` | 截图文字识别 | macOS 系统 Vision；其他系统不可用 |
| `commands` | 领域命令，挂在 `acceptkit <命令>` 下，不能覆盖内核命令 | 命令不存在 |
| `qualityRules` | 项目特有的用例质量规则，追加在通用规则之后 | 只用通用规则 |
| `newCaseTemplate` | 新建用例的骨架（切面分类） | 内核通用骨架（或配置 `newCase.classifications`） |
| `dashboard` | 用项目自己的看板生成器（相对路径） | 内核看板 |

闸门白名单是**数据**，写在项目配置的闸门段：允许的设备、包名、租户，以及「仅在某平台放行」的条件项。识别不出目标 = 拒绝。

## 5. 观测降级

观测降级的做法是：断言的观测规格可以声明后备通道，主通道用不了时按后备走，每个通道有强度，低于要求的不记通过。规格写法：

```json
"observe": { "op": "diag-query", "pick": "...", "pass": { "eq": "block" },
             "fallback": [ { "op": "log-grep", "pattern": "action=block" } ],
             "min_strength": "S2" }
```

| 强度 | 通道 | 判定 |
|---|---|---|
| S1 | 被测对象主动暴露的诊断接口 | 机判 |
| S2 | 日志、网络、页面内容、产物文件 | 机判，间接证据 |
| S3 | 截图 → 文字识别 → 谓词 | 机判，可能被界面误导 |
| S4 | 人工检查 | 人判 |

每条结论记录实际使用的通道与强度；低于断言要求的最低强度不记通过，记阻塞。

## 6. 知识与账号

知识是项目知识目录里的普通 Markdown 文本，可以带平台等标签。标成机密的值，工具层在写证据、报告、日志时统一替换成星号。

测试账号的值也是机密，但不放进知识，单独存，有专门的账号命令管理；清单和值都在这台机器的用户配置目录里（只有本人可读），不进项目目录 —— 项目目录会被共享、打包、开源扫描。元数据（id、类型、平台、登录方式、说明）可以列出；其余字段都是机密，列表不打印，写证据和报告时同样换成星号。知识条目可以标状态：推测 / 已确认 / 已验证。

## 7. 被测 App（宿主）与设置：构建与驱动

### 宿主

一个项目可以在多个 App 里验同一个被测物（同一个引擎嵌在主 App 和示例 App 里），新 App 也会随时加进来。所以「每个 App 一份」的东西都按**宿主 id** 存，不按平台存：按平台存时同一平台只能放一个 App，第二个 App 进来只能覆盖第一个。

```json
"hosts": {
  "main": { "title": "主 App", "ios": { "bundle": "com.example.main" }, "android": { "package": "com.example.main" } },
  "shop": { "title": "商城 App", "android": { "package": "com.example.shop" } }
}
```

| 按宿主存的 | 位置 |
|---|---|
| 包名 / bundle / 调试端口 | 项目配置 `hosts.<宿主>.<平台>` |
| 构建做法 | `knowledge/settings/<平台>/<宿主>/build.md`（每个 App 一份） |
| 驱动做法 | `knowledge/settings/<平台>/driver.md` 同平台共用；某个 App 用不了时写它自己的 `…/<平台>/<宿主>/driver.md`，优先于共用的 |
| 只在某个 App 上成立的操作配方 | 操作库的 `<平台>@<宿主>` 键，优先于通用的 `<平台>`；写 `absent` 表示这个 App 上做不了，通用做法也不套用 |

用例和白名单设备引用的宿主都是这里登记的 id，没登记的报错。用例两端不是同一个 App 时，按平台分别写。

**这一步用哪个宿主**：显式指定（命令行、用例、设备声明）→ 该平台只登记了一个宿主时就是它 → 有多个又没指定时报错，不挑第一个。同平台登记了多个宿主而用例没写宿主，用例质量检查拦下新用例（基线里的存量用例只提示）；此时只能用通用配方，宿主专属的配方、包名、构建都取不到。

**新 App 借鉴别的 App**：借鉴命令把对方当前生效的那份拷成新 App 自己的文件，状态「推测」，说明里注明借鉴自哪里。可以试跑推测的做法；试跑通过**不自动升级**（退出码 0 不说明产物是这个 App 的包），核对后写明核对了什么才升为已验证。走不通就改新 App 自己的那份，被借鉴的一方不受影响。不做运行时继承：继承时源头一改，借用方跟着悄悄变，也说不清当前生效的是谁的做法。

旧写法（每个平台只能放一个 App 的那套配置）由体检命令的修复模式迁移，但只在能确定归属时迁：用例里写到的宿主超过一个时，旧配置里各平台属于哪个 App 机器猜不出来，报出来让人拆。

### 设置

流程是确定的，所以流程要用的设置位置也是固定的（见上表）。设置项、必需动作与作用范围（每个宿主一份 / 同平台共用）在内核里集中登记一处。不在其他知识里按标签或关键词搜：流程能用什么命令，只由这个位置的文件决定。

```markdown
# iOS · 驱动 App

- 状态：已确认
- 来源：被测 App 仓库里的 docs/debug.md

## 命令

- ui-tree: `mytool fetch --json -p {port}`
- tap: `mytool tap -p {port} --text {text}`

## 说明

（注意事项、踩过的坑：给人和 agent 读，不参与执行）
```

- 「命令」一节下每行一个动作；端口、设备号、包名、仓库、文字这些占位符由调用方填，值按 shell 转义，不会被当成命令解释。
- 写入时检查必需动作；状态为推测的设置不执行（确认后才用，或显式试跑一次）。
- 构建和驱动命令照设置执行，包名按这一步的宿主填；扩展包通过内核给的驱动入口调用，代码里不出现工具名。内核读 UI 层级时，如果没有扩展解析器，就直接用「读界面树」这个动作的输出。
- 每个登记的宿主 × 它的平台都要有设置；体检、设置查看、登记宿主、知识概览都会列出缺口，前三个还会列出本项目里可以借鉴的宿主。

## 8. 管理页面

管理页面是 acceptkit 自己的本机网站，不依赖别的页面嵌入（启动命令和缺省地址见文末附表）：

- 首页列出登记过的项目：用例数、最近一次运行。
- 每个项目一个看板页，链接可以直接停在某份报告上。首屏只给目录和面板空壳，切到哪一面才渲染哪一面：每个项目一个常驻看板进程，项目数据有变化才重新读数据（大项目约 2 秒），渲染过的面板在这一代里缓存；半小时没人看就收掉。常驻进程要把整个项目的数据留在内存里：本机一个 600 多个运行的项目约占 300–440MB。项目自带的看板脚本仍是一次出整份 HTML、再拆成面板。
- 截图按需出（只出项目目录里的图片），不内联进页面：大项目内联后页面会超出字符串上限。
- 只听本机。看板里是被测系统的内部数据，要对外开放得显式指定监听地址，并会提示。
- 打开报告、取报告链接的命令缺省指向它，没在跑就在后台起一个。看板另外嵌在别的页面里、要给那个页面的地址时，才配看板地址；项目自己的看板生成器按运行 id 定位时，配定位方式。
- 改了内核代码后先停掉它，下次打开会用新代码重新起。

## 9. 用户设置的其他东西：写口与校验

操作库、项目配置、知识都是用户设置进来的。规则一样：

- **有写口**：操作、配置、宿主、知识、项目登记都有各自的增删改命令（见文末附表）。
- **写入时校验，不合格不落盘**：操作要有平台中立的标题与理由；配方只能挂在某个平台、或某个平台上登记过的宿主下；「这个平台做不了」的配方要写清卡在哪；配置键按内核登记的类型检查（白名单项要有类别与说明，端口是正整数，正则能编译）。未登记的参数直接拒绝，不静默收下。
- **手改的文件过同一道检查**：操作检查、配置检查、体检。问题分两级：结构错误（读的一方会用错，比如白名单项 kind 写错会让它静默失效）和不认识的字段（没有读者，写了等于没写）。
- **配方有状态**：推测 / 已确认 / 已验证，推测的配方在执行时返回错误（「确认后才用」）：断言的主通道是推测配方时，观测直接报错退出、不落结论；只有后备通道或前置条件用到推测配方、且所有通道都走不通时，才记为阻塞。旧写法由体检的修复模式迁移。

## 10. 主要设计选择：当时的备选与风险

前面各节写的是现在怎么做。下表补上三处主要选择当时比过什么、为什么这么选、要承担什么。产品层面的取舍（工具箱还是自带 agent、宁可判不了也不错判通过等）见 [000-philosophy.md](000-philosophy.md) 的「取舍」一节，这里不重复。

| 选了 | 没选 | 为什么 | 风险 / 代价 | 什么时候重新考虑 |
|---|---|---|---|---|
| 文件 + SQLite 混存（第 3 节） | 全部进 SQLite；全部用文件 | 用例、结果、评审单要人能读、能 diff，项目自带的脚本可能直接读写这些文件；租约、审批要事务，文件做不到并发安全 | 两种存储要分别维护；有人绕过 CLI 手改文件，SQLite 里的派生索引会旧，要靠索引命令校验、重建 | 项目里直接读写文件的脚本都改成调 CLI 后，逐个实体切成 SQLite 正本（第 3 节） |
| 一期先做 Skill 入口，内置 Agent 放二期（第 1 节） | 一上来自带对话循环和模型 | 用户手上已经有编码 agent，不用另配模型就能用；验收规矩写在工具层，换入口不用重写 | 没有自己的循环，只能靠卡片和钩子推着 agent 走；钩子只覆盖支持钩子的宿主 | 有不在编码 agent 里工作的用户、或要无人值守跑时（第 11 节二期） |
| 本机网站做管理页面（第 8 节） | 嵌进别的页面；做服务端 | 不依赖别的系统就能看；看板里是被测系统的内部数据，只听本机最稳妥 | 大项目常驻进程占 300–440MB；多人看同一份看板要靠共享项目目录 | 团队共享阶段换成服务端数据库时（第 11 节「之后」） |

出了故障时会怎样：

- **SQLite 库坏了**：索引从文件重建，不丢东西；但设备租约、审批记录、环境快照的正本只在库里，内核没有备份，库坏了这几类会丢，审批记录丢了就说不清谁凭哪句原话批的。并发写靠 WAL 模式和 5 秒忙等，不靠文件锁。
- **看板进程挂了**：不影响验收本身（判定和闸门都在 CLI）；下次打开报告时会在后台重新起（第 8 节）。

## 11. 演进

演进分三期，现在是一期：

| 阶段 | 内容 |
|---|---|
| 一期（已落码） | 本机 + Skill 入口；文件正本 + SQLite 租约/审批/快照/索引 |
| 二期（未开始：内核里还没有调用模型的代码，也没有实体切换过） | 内置 Agent（需要配模型）；脚本迁移后实体切换为 SQLite 正本；多端对比 |
| 之后（未开始） | 团队共享（服务端数据库）、执行机注册、托管 |
