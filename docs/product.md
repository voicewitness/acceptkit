# acceptkit 产品目标

## 一句话

acceptkit 是一个**本机运行的验收 Agent 工具箱**：研发或测试在自己的编码 agent 里加载 acceptkit skill，由 agent 驱动一套不调用模型的验收工具，在真实的 App、浏览器、模拟器上执行验收，并留下可复核的证据。

## 解决什么问题

传统用例是一句抽象的话，靠人脑理解后映射成操作，再靠人眼判断结果。acceptkit 把用例变成：

- **人能读懂的执行标准**：用例是一棵操作树，每个节点是一步人话操作，节点上挂断言；
- **机器能执行的判定方式**：断言自带观测规格（怎么观测、取什么值、什么算通过），由工具执行、原文落盘、按规则判定；
- **自带适用范围**：断言声明适用的版本、平台、宿主，选取和判定时自动计算。

## 价值点

| 价值 | 说明 |
|---|---|
| 用例资产 | 人话 + 执行标准 + 适用范围，同一份文件人和机器都能读 |
| 用例质量 | 新增 / 修改用例按统一标准检查（[case-quality.md](case-quality.md)），不达标不能批准、不能开跑；存量问题记为质量债 |
| 用例评估 | 新需求执行 / 旧用例回归：按需求的评审单决定跑哪些用例，未批准不允许运行 |
| 执行效果 | 准、全；复核服务于执行（驳回的断言退回重测），不服务于报告好看 |
| 报告 | 结果的投影：每条结论可以点到证据 |
| 存量迁移 | 历史用例导入并逐条转成执行标准，条数守恒、不可判定的如实标出 |
| 用例生成 | 需求 → 改动面 → 复用 / 新建，进评审单 |
| 多端 | 同一用例跨平台适用性由机器计算；端到端链路在同一棵树里 |

## 定位与范围

- **一期**：本机部署 + Skill 入口。不需要常驻服务，不需要配置模型（模型由宿主编码 agent 提供）。
- **二期**：内置 Agent（给不在编码 agent 里工作的用户、无人值守运行），需要配置模型。
- 不做：托管、多租户、团队共享数据库（见 [architecture.md](architecture.md) 的演进说明）。

## 用户与环境

acceptkit 必须在完全不同的用户环境里都能冷启动：

| 环境 | 手上有什么 | 最大风险 |
|---|---|---|
| 只有代码 | 本地仓库、dev server | 把开发环境的外部调用真的打出去 |
| 只有安装包 | apk / ipa、设备、旧用例表格 | 测错版本；动了个人设备 |
| 大仓 + 多宿主 | 巨型仓库、多个宿主、debug 诊断通道 | 设备被占用；用错宿主；采集开关时序 |
| 内网配置后台 | SSO 后台、测试租户 | 误操作生产租户；用接口绕过页面造成假通过 |

冷启动结束时，Agent 必须回答五个问题，每个答案都带来源：

1. **我到底在测哪个东西？**（包名 + 版本 + 构建来源 + 宿主）
2. **我能动哪里、哪里不能动？**（设备、租户、账号、危险动作）
3. **我怎么看到结果？**（每种观测方式能否使用、前提条件）
4. **怎么把它带到可测状态？**（装包、登录、要不要构建；构建方式和驱动工具写成设置）
5. **什么算真的验过？**（哪些捷径不算数）

## 用户可设置的能力

验收流程是确定的：构建 → 装包 → 启动 → 驱动 App → 观测 → 判定。流程里有些步骤怎么做因项目而异，例如大仓 App 只能用仓库自带的构建脚本、iOS 端用 App 内置的调试 SDK 驱动。这些**不写进产品代码，由用户设置**；流程执行到那一步时，按固定位置读取对应的设置。

| 设置项 | 流程里哪一步用 | 必需动作 | 位置 |
|---|---|---|---|
| 构建 | 把被测对象构建出来（改了会进包的代码、或用户要求时） | `run` | `knowledge/settings/<平台>/<App>/build.md`，每个 App 一份 |
| 驱动 App | 操作 App、读 UI 层级（截图前的遮蔽层检查也用它） | `ui-tree` | `knowledge/settings/<平台>/driver.md` 同平台共用；某个 App 例外时写它自己的 `…/<平台>/<App>/driver.md` |

- **怎么设置**：
  - 对 Agent 说「iOS 用这个脚本构建」，Agent 照这句话写入设置；
  - 或者直接运行 `acceptkit setting set build --platform ios --run "<命令>"`；
  - 也可以手工编辑上表里的文件。
- **怎么发现**：冷启动时 Agent 读仓库和文档，找到官方构建方式和调试工具，写成「推测」设置。推测状态的设置不执行，由用户确认。
- **缺了怎么办**：`doctor` 和环境画像会列出缺哪项设置；流程执行到缺设置的那一步时，停下来问用户，不自己拼命令。
- **一个项目可以有多个被测 App**（`acceptkit host add`）：每个 App 的包名、构建做法各存一份，加进来的新 App 不会覆盖已有 App 的。
- **新 App 可以借鉴**：刚加进来时，可以从同项目或别的项目里的 App 借一份构建 / 驱动做法（`setting borrow`）。借来的是新 App 自己的一份拷贝，标「推测」；试跑通、核对过产物再升级成已验证。走不通就改它自己的那份，不影响被借鉴的 App。
- **一项设置一个文件**：同一个 App 的同一项只有一份，重新设置就覆盖。流程只读这个位置，别处知识里写的构建方式不会被执行。

流程设置之外，下面这些也是用户设置进来的。每一类都有写口，写入时校验；手工改的文件过同一道检查（`doctor`，或各自的 `check`）。只能手改文件时，新发现的做法往往没人写回去，写回去时字段也各写各的，读的一方认不出就静默失效。

| 东西 | 例子 | 写口 | 检查 |
|---|---|---|---|
| 操作库：每个操作在各平台怎么做 | 「Android 登录页连点三次 logo 能进调试菜单」 | `ops set <id> --platform P --how …`；平台做不了写 `--absent "<原因>"` | `ops check` |
| 项目配置 | 允许操作的设备 / 包名 / 租户，被测 App 的包名，项目特有的危险动作词 | `config set` / `config add` / `config rm` | `config check` |
| 知识 | 账号、注意事项 | `know add` / `know edit` / `know rm`（改写机密条目时自动保留 `#secret`） | `doctor`（文件权限） |
| 缺省项目 | 不在项目目录里启动时用哪个项目 | `project use <dir>` | — |

- 操作的配方也分推测 / 已确认 / 已验证：Agent 自己推测的写 `--guess`，推测的配方不执行；实测跑通的写 `--verified "<什么时候在哪跑通>"`。
- 删一条还被用例引用的操作会被拒绝。

## 原则

- **要测哪个项目由用户决定**；环境由 Agent 检测。
- **能发现的不问**；要问时先说明已经试过什么。
- **知识带来源和状态**：推测 / 已确认 / 已验证。推测不用来做决定。
- **危险动作先停下问**；闸门在工具层强制执行，不依赖 Agent 自觉。
- **缺口如实写**，并说明对结论可信度的影响。
- **取证手段自己坏了不算发现**：它与被测物的失败分开归类、单独计数，不混进汇报内容，也不压低结论。
- **Agent 不能替用户批准任何东西**。
