# 000 理念

## 要解决的问题

编码 agent 已经能自己点 App、开浏览器、读日志。让它「去验收一下」，它几分钟就能回一句「验过了，通过」。
难的不再是「能不能操作」，而是**这句「通过」能不能信**：

- 它点的是不是被测的那个包、那台设备？
- 截图里是结果页，还是一个登录弹窗？
- 「没看到报错」是真没有，还是没去看？
- 它判的是需求要的行为，还是它自己理解的行为？
- 这次踩过的坑，下次换一个会话、换一个 agent，还会不会再踩？

市面上的工具各解决一部分：

| 类别 | 擅长 | 留下的问题 |
|---|---|---|
| 脚本化 E2E（Appium、XCUITest、Espresso、Playwright） | 确定、可重复 | 写和维护都贵，界面一改就断；只验脚本写到的东西；新需求要先写脚本 |
| AI 测试 agent（让模型直接操作界面并给结论） | 灵活，不用写脚本 | 结论是模型说的：没有可复核的证据，没有「什么才算验过」的标准，经验留在一次对话里 |
| 用例管理平台 | 管用例、管状态 | 用例是一句抽象的话，执行和判断全靠人 |

## acceptkit 的目标

**让 agent 做出的验收结论可信、可复核、能积累。**

- **可信**：结论不超出证据。没有证据的「通过」不能被记下来；错判成通过是红线，宁可记「判不了」。
- **可复核**：每条结论都能点到当时落盘的原始证据，由没参与执行的人或 agent 重新判一遍。
- **能积累**：操作怎么做、什么样的证据算数、哪些坑踩过，都沉淀成项目的数据，下一次执行直接用上，不依赖某个会话的记忆。

附带的原则：**人的注意力只花在只有人能做的判断上。** 要测什么、产品该怎么表现、危险动作能不能做，由人定；
其余的发现、操作、取证、复核，由 agent 和工具完成，并且问人时一次问清一件事。

## 为什么是「工具箱」，而不是又一个 agent

acceptkit 自己不调用模型，也不运行对话循环。用户用的是哪个编码 agent（Claude Code、Codex、Cursor……），就由那个 agent 来执行。

- **模型和循环换得掉，验收的规矩换不掉。** agent 每隔几个月就换一代，而「什么算验过」「这个项目的坑在哪」是项目自己的资产。把资产放在 agent 之外，换 agent 不丢。
- **只有模型能做的事交给模型，其余交给代码。** 把人话操作对到一个不断变化的界面上、读懂需求的意思，只有模型做得了。
  但「现在该做哪一步」「这台设备能不能用」「这条结论有没有证据」「这件事要不要人批」是可以算出来的，算出来的就不该靠模型自觉。
- **代价是我们没有自己的循环。** 所以循环写在提示里：agent 每一轮先问工具「还剩什么」，照工具给的卡片做一步，再问。
  状态全在磁盘上，一轮中断了，下一轮（或换一个 agent）从磁盘接着做。见 [002 协议](002-protocol.md)。

## 由此推出的设计

- **代码定，模型判。** 谁、何时、在哪、做几个、什么状态由代码定；意思（意图、范围、相关性、措辞）由模型判。
  模型只能通过命令出手，命令在代码里再查一遍；能由代码先给出候选的，代码先给，模型确认或否决，否决了代码给下一个。
- **证据由工具产出。** 能由工具观测和判定的，由工具执行并把原文落盘；只能由 agent 判断的，agent 交出它看到的原文和逐条判断，结论由工具按规则算。
- **像 QA 一样验。** 结论默认在界面上看：读到结论那一刻的 app 截图，人一眼看得懂、也难伪造。日志、调试器这类命令行手段只用在界面上确实看不到的断言上，事先写明理由、评审时给人过目，证据也要由工具亲自采。
  缺证据和验不了是两回事：缺证据就重试补齐，不算通过，也不改记成验不了。
- **执行者不复核自己。** 自己刚看过的证据最容易被放过，复核交给一个只看证据包的新上下文。
- **经验是数据，不是长篇手册。** 能变成检查的，变成检查；只能靠判断的，存成可以按需取用的知识，执行到那一步时由工具递给 agent。手册只讲循环和几条铁律。
- **取证手段坏了不是发现。** 超时、连错设备、抓到上一轮的日志，是工具自己的失败，单独记、单独计数，不算被测物的问题。
- **概念少。** 业务需要先变成已有概念的一个属性，变不了才加概念。
- **手册守不住的，交给宿主钩子。** 「设备只由 acceptkit 起」「验收记录只由命令写」「没做完别停」写在手册里，执行者照样会绕开。
  能在宿主上拦的（跑命令前、写文件前、要停下时）装成钩子，由宿主强制；钩子坏了一律放行，不能把 agent 锁死。
- **知识先判层：工具 / 项目 / 用户。** 对所有用户都成立的才进 acceptkit 的代码和手册；只对一个项目成立的进项目知识；
  只对一个人、一台机器成立的（代理规则、显示器、测试账号的值）进他自己的用户配置。判错层的代价是把一个人的环境当成所有人的规矩。
- **人的身份就是这台电脑的主人。** 在看板上点一下「同意」就算本人点头（页面只能由本机发起写回），不用再自报姓名；
  但给人拍板的东西必须是他能拍板的：写清是什么、影响什么、有哪几个选项和各自的后果、推荐哪个。

## 责任

agent 在真实的设备、账号和测试租户上动手，它的结论会被拿去决定能不能上线。

- **从窄处开始。** 白名单只放允许动的设备、包和租户；危险动作先停下问。
- **报告如实。** 判不了就记判不了，并写清卡在哪、怎么解锁；缺口要写出来，并说明它削弱了哪条结论。
- **出了错，改规则，不改说法。** 一条结论被复核驳回，先问是哪道检查漏了，把检查补上。

## 路径：为什么是这个顺序

每一步都是被上一步暴露出来的失败推着走的，顺序就是「先让结论能信，再让流程不靠记性，最后让人只做人该做的」。

1. **结论只认证据。** 先有闸门：没有证据的 pass 记不下来，证据由工具落盘，复核交给盲审。没有这一步，后面一切都建在一句「验过了」上。
2. **状态在磁盘上，下一步由工具算。** 有了证据还不够：会话一断、换个 agent，做到哪了就说不清。于是有了命令清单（类工具调用的协议）和 `next` 卡片，
   agent 每轮只问「还剩什么」，停不停也由工具说了算。
3. **人只看能拍板的东西。** 流程跑顺以后，最贵的变成了人的注意力：评审单只给增量、finding 和阻塞必须写成选择题、看板按「等你 / 正在测 / 完成」分泳道。
4. **规矩由宿主强制。** 手册里的铁律仍然会被绕开（手动起设备、手改记录、问完就停），于是把能拦的装成宿主钩子。
5. **分清谁的东西。** 开源要求工具里不能有任何一个人、一个组织的环境：用户偏好、测试账号、项目知识各归其位。

## 取舍

| 选了 | 没选 | 为什么 | 代价 |
|---|---|---|---|
| 工具箱，借用户已有的 agent | 自带 agent 和模型 | 模型和循环几个月一换，验收的规矩是项目资产，要能活过换代 | 没有自己的循环，只能靠提示 + 卡片 + 钩子让 agent 持续推进 |
| 代码定流程、模型判意思 | 让模型自己决定下一步 | 「该做哪步、能不能做、要不要人批」算得出来，算得出来就不该靠自觉 | 流程改动要改代码，不像改提示那么快 |
| 宁可判不了，不错判通过 | 尽量给出结论 | 错判成通过会被拿去上线，判不了至少会有人去看 | 报告里「验不了」会比较多，要人去解锁 |
| 本机、零依赖（Node 内置 SQLite） | 服务端、数据库服务 | 验收要碰本机的设备、账号和登录态；装不上就没人用 | 多人协作要靠共享项目目录，没有中心服务 |
| 每条规矩先变成检查 | 写长篇手册 | 手册越长越没人照做，检查不会忘 | 加一条规矩要写代码和测试 |
| 钩子出错放行 | 钩子出错就拦 | 钩子坏了把 agent 锁死，比漏拦一次更糟 | 钩子坏的那段时间约束会失效，靠测试和 `hook list` 发现 |

## 已知的不足

- 钩子只覆盖支持钩子的宿主（Claude Code、Codex、Gemini CLI、Cursor），而且只能拦它看得见的动作：脚本内部起的进程拦不到。
- 设备窗口开在哪块显示器，目前只对 Android 模拟器生效；iOS 模拟器的窗口位置按显示器存，还没做。
- 证据能否证明结论，最后一道仍是盲审 agent 的判断；工具能保证证据是原文、是当时的，保证不了它被读对。
