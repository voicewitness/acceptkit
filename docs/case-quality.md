# 用例质量标准

用例是资产：一条用例写坏了，每次执行都会产出坏结论。所以每次新增或修改用例，都按同一套标准检查。规则来自成熟用例库里反复出现的坏写法，每条都写明「教训」，也就是违反它在历史上导致过什么。

规则的正本是 `core/case-quality.mjs`，`acceptkit quality --standard` 打印当前项目实际生效的规则，包括项目扩展追加的规则。

## 什么时候检查

| 时机 | 做什么 |
|---|---|
| `acceptkit new` 新建用例 | 打印标准和自检问题，照着写 |
| `acceptkit validate <case>` | 按规则检查；有不达标项退出码 1 |
| `plan check` / `plan approve` | 评审单里任何一条用例不达标都算硬错，不能批准；同时列出评审时要逐条问的问题 |
| `acceptkit run` | 不达标的用例不能开跑（调查类 probe 用例除外） |
| `acceptkit quality` | 全量盘点：新问题、存量质量债、已豁免 |

## 两档

- **✗ 拦截**：新增或改过的用例不达标，就不能进评审单批准，也不能开跑。
- **⚠ 提示**：列出来，由作者确认。

## 存量用例

引入标准时已经存在的用例，用 `acceptkit doctor --fix` 登记基线。基线里已有的问题记为**质量债**，只提示，不拦截。改过的存量用例只拦**新增**的问题，不会因为改了一个字就把旧债全部变成拦截。新项目（`project init`）的基线是空的，每条用例都按标准拦。

## 例外

个别断言确实要例外时，在断言（或节点、用例）上写明理由：

```json
"quality_waive": [{ "rule": "Q04", "why": "这条是计数为 0 的契约断言，对照在兄弟断言 E3 里" }]
```

豁免会在检查结果里显示为「已豁免：理由」。没写 `why` 的豁免不生效。

## 通用规则

| 规则 | 档 | 坏写法 | 教训 |
|---|---|---|---|
| Q01 断言要有判定方式 | ✗ | 没有 `observe`，只有一句文字判据 | 没有机器判据的断言大多落成「待测」或「阻塞」；判据临场想，两次执行判法不同。确实只能人判，写 `judge: "human"` 和 `human_why` |
| Q02 断言必须可判定 | ✗ | 「启动正常」「有相关输出」、模板占位 | 执行人按自己的理解判，通过了也说明不了什么 |
| Q03 一条断言只判一件事 | ⚠ | 一条断言三个子句，判据只有一条 | 证据只证明了其中一件，复核按「证据不足 / 夸大」驳回 |
| Q04 阴性判定要有前提 | ✗ | 「没出现 / 计数为 0」，没有 guard | 功能根本没跑、开关没生效、数据被淘汰时同样成立，平凡通过 |
| Q05 提交成功不等于生效 | ✗ | 只断言「保存成功」「code=0」，之后没有回读 | 页面提示已保存，重新打开值没变：出过假通过 |
| Q06 危险写操作要结构化标记 | ✗ | 「发布 / 删除 / 清空」只写在操作文字里 | 执行到一半才发现要人确认，整段记阻塞。写 `danger: { kind, confirm }` |
| Q07 全新安装类断言要标卸载 | ⚠ | 断言要求全新安装，没标 `requires_uninstall` | 卸载会清掉登录态，必须单独审批 |
| Q08 依赖的前置状态要写明 | ⚠ | 要求「默认关闭」，没写前置也没有 guard | 上一轮改过状态没复位，下一轮直接阻塞或误判 |
| Q09 用例里不写执行状态 | ✗ | 用例里有 `status` / `blocked_on` / 「当前必红」 | 执行状态属于某一次运行，写进用例会被下一轮当成规格 |
| Q10 不用自造字段 | ⚠ | 切面写成 `classify`、字段拼错 | 工具不认，覆盖统计看不见，静默失效 |
| Q11 对照分支的预期不能一样 | ✗ | 开关两档的分支写着同样的断言 | 两个分支都通过，测不出开关有没有起作用 |
| Q12 主张要逐条有断言支撑 | ⚠ | 主张的 `proved_by` 列了全部断言 | 等于没说哪条证明了它，复核无从下手 |
| Q13 页面判定不读整页文本 | ⚠ | `observe` 读 `document.body.innerText` | 整页文本里有背景页、隐藏层的旧内容 |
| Q14 硬预期值要有出处 | ⚠ | 断言里写死数值，没有 `source` | 分不清是被测错了还是预期写错了 |
| Q15 同平台有多个被测 App 时要写在哪个 App 上跑 | ✗ | 用例没写 `host`，而该平台登记了多个 App | 只在某个 App 上成立的做法、它的包名和构建都取不到；「这个 App 上没有」分不清是被测物还是 App 的特性 |

| Q16 用例正文说人话，不用行话 | ✗ | 标题、为什么、操作、断言里有「臂 A」「两臂」这类要先学才看得懂的词 | 断言是要念给人听的验收结论；括号里已经是人话时，前面的行话只是多余的门槛 |

| Q22 断言里说的效果要在那一层看到 | ✗ | 断言写「拦截 + 弹窗」，观测只读了判定记录里的动作名 | 工具机判通过、盲审也放行，弹窗弹没弹、请求拦没拦从没人看过。收窄说法，或补一条读那一层的观测（见下「观测层」） |
| Q23 判「没有」要先证明被判的那个对象在 | ✗ | 读某个 unit 的动作判「没有」，前提只证明了「整页评估了 10 项」 | 这个 unit 根本没执行时读数同样是空，照样通过。前提要读同一个对象、证明它在 |
| Q24 开关类用例的判据要分得出对照 | ⚠ | 开关用例里判据只看「有值 / 大于 0 / 等于 0」 | 开关开和关两档下都成立，测不出开关。写 `observe.flips_in`（在哪个对照节点下它会不成立），或换成只在这一档才有的读数 |

| Q26 说了上报 / 拦截 / 生效的用例，至少要有一条判内容 | ✗ | 这几条断言的判据全都只看「有没有」 | 同样的输入就该得到同样的输出：只判「有上报」，上报里的字段全是空值也照样通过。挑一条最关键的判到字段和取值；业务上确实只测有没有的写 `why_presence_only` |
| Q27 说了上报 / 拦截 / 生效，最好判到内容 | ⚠ | 某一条只判了有没有 | 用例里别的断言判了内容，这一条上照样会漏 |

| Q28 断言只写一句话 | ⚠ | 断言超过 80 字、分了好几段，或者出现两个以上代码名 | owner 读不懂就批不了。读数位置和依据写进 `detail`，修订记录写进 `history` |
| Q29 断言多的用例要有结论树 | ⚠ | 4 条以上断言没有 `claims`，或者有断言没挂到任何结论上 | 操作树按执行顺序排，看不出这些断言合起来要证明什么 |
| Q30 结论树每层写结论，不写做法 | ⚠ | 主张超过 40 字、出现两个以上代码名、写成了步骤，或者一层挂了 7 条以上 | 结论树又退回成看不懂的清单 |

| Q35 一步只写一件事 | ⚠ | 步骤文字超过 40 字，或连着写了几个动作（分号、箭头、「然后 / 再」） | 读的人分不清哪一步做了什么、截图该对哪一步。几个动作拆成几个节点，要填的值写进 `params`，为什么写进 `note`，常用的一串步骤登记成操作挂 `op_id`（看板上点开就是那串步骤） |
| Q37 每一步、每条预期都要有操作步骤 | ✗ | 预期没写 `see`、观测操作也没有人看的步骤；或一步是没填的模板 | 第一次写也大致知道进哪一页、看什么，先写大致的，跑过后改准 |
| Q38 操作步骤要准 | ⚠ | 步骤说不出「动作 + 对象」、写着裸命令；`see` 说不出具体看哪里；「看」的步骤括起来的只有要找的对象（参数值，如 unit 名）、没写页面上读得到的字段或行（如「看「app2app_report」的执行路径」—— 页面上叫 `path=`），观测操作自己的人看步骤同样查 | **跑过一次以后必须改准或判不可执行**，否则这条用例不能再开跑；`clarify <用例>` 给出那次执行的事实和写回命令，命令用 `--to-op` 提成操作集；同一个看法（换个对象还是这么看）建成带 `{param.x}` 的读法操作，用例写 `@<操作>` + 这一条自己的判据，检查会指出已有的读法操作 |
| Q36 配置写进配置集，不写在步骤里 | ⚠ | 步骤文字里有 `名=值` 的开关 / AB / mock 值，或引用了不存在的配置集 | 读的人分不出配置和操作，两组用例差在哪只能逐字对。`acceptkit configset set <id> --item 名=值 --kind mock|env --why …`，用例或那一支节点写 `config: [<id>]` |
| Q31 每一步都要说清怎么触发 | ✗ | 操作树上某一步没挂登记了 `--input` 的操作、节点上也没写 `input`，用例上也没整体声明 | 评审时谁也看不出这一步是不是在注入。说不清的不算真实 |
| Q32 一条用例至少要有一条断言经真实路径触发 | ✗ | 有直接注入的断言，却没有一条整条链都是真实路径（或只 mock 全局信号）。评审单里一个改动面合起来也这样，`plan check` 不通过 | 和单测没区别：真实路径上组装输入的那一段一次都没走过 |
| Q33 直接注入的断言只算低分证据 | ⚠ | 每条注入的断言（机判、人判都算） | 注入时手写的字段正是真实世界里要由系统自己算的 |
| Q34 手写的输入字段要说清全局还是调用点 | ✗ | 步骤文字 / 数据 / 观测参数里手写了 `{k=v}` / `{"k":…}` 的字段没在 `input.mocks` 里说清 `scope`（global 全局信号 / call-site 调用点字段 / tool 操作自己的参数）；mock-global 没写 `why`；调用点字段没写理由、或没有 `real_twin` 指向一条真实对照（real，或只 mock 了全局信号的） | 替系统把最容易出错的那一步做了 |

Q15、Q16、Q22–Q24、Q26、Q27、Q31、Q33 是基线登记之后加的（`since`）：对基线里的存量用例只提示，对新用例照常拦。Q28–Q30 在试行期，对所有用例都只提示。Q32、Q34 对存量用例也拦。

**触发方式**是操作树上每一步的属性，不是证据的属性：输入是假的，判得再准也只证明「输入对了判定就对」。三种 —— `real`（经真实用户 / app 路径触发，包括 app 自带工具发出的真实请求）、`mock-global`（只 mock 全局信号，如全局特征、AB / 配置值）、`injected`（把构造好的输入直接交给判定入口，绕过系统自己组装输入的那一段）。

每一步按顺序认：节点上写的 `input` → 节点 `op_id` 在操作库里登记的（`acceptkit ops set <op> --input …`）→ 文字或数据里手写了输入字段就算注入 → 用例上整体写的 `input`（只补说不清的）→ 说不清。一条断言取它整条链（加上观测操作、断言自己的声明）里最假的；说不清排在只 mock 全局和注入之间，不算真实。

```json
"input": { "from": "injected", "why": "…",
  "mocks": [{ "field": "…", "scope": "global|call-site", "why": "…" }],
  "real_twin": "E8",
  "research": { "tried": ["…"], "alt": "…", "verdict": "found|none" } }
```

**用例评审时就查**：`next` 对不是真实触发的步骤出 trigger_consult 卡片。`acceptkit consult <用例> [--node <节点>]` 在被测仓（`round repos` 登记的）里找手写字段在哪算出来、调试 / 工具代码和项目脚本里哪里碰到它们；执行者顺着往上追到真实情况下产生这个输入的入口，写成测法建议（`--propose --real --evidence --how --catches [--prep]`），owner 在卡片上看到「真实情况下什么产生这个输入、代码依据、建议怎么测、要不要先补东西、能多验到哪一段」，定改不改（`consult decide`）。评审单和评审稿上按改动面列出几条真实、几条注入、几条说不清。
**两棵树**：一条用例有两棵树，靠断言编号连起来。

- **结论树（`claims`）是给人读、给 owner 批的。** 根写这条用例要证明什么，`children` 写分哪几方面，叶子的 `proved_by` 写由哪几条断言证实。每层叫什么由写用例的人定，工具只检查形状。
- **操作树（`tree`）是给执行者按顺序跑的。**

断言本身只留一句话，写清功能坏了这条会不会失败。读数位置和源码依据放 `detail`，改过几次放 `history`（`[{ at, text }]`）。看板默认只显示那一句，另外两样折叠起来。

`acceptkit tidy <用例>` 会把断言原文里带日期的修订段落挪进 `history`，一个字不改，所以批准后这样改直接通过。它还会列出还要改写成一句话的断言，以及结论树缺什么。改写成一句话属于「验的范围变了」，批准后改要写理由，旧结论作废重测（不找 owner，见 `plan recheck`）。

**观测层**：断言里的效果词（内核自带：弹窗、拦截、上报、不崩、生效）要有读到对应层的观测才算证明了。观测操作登记它读的是哪一层：`acceptkit ops set <op> --observes decision|diag|ui|network|report|crash|state|log|source|perf`（某端读的层不同，写在那份配方上）。项目自己的效果词：`acceptkit config add quality.claimWords …`（`{ word, match, covers }`）。效果词讲的是一个部件时不算主张（「上报环里的记录」「上报出口」「上报路径」，同一句后面再提这个词也一样），断言自己声明「这条不判」的那一句也不算；还有别的情况，在断言上写 `claims_off: [{ word, why }]` 说清楚（盲审照样看得到，原文读下来就是效果的照样核；这个改动要 owner 认）。

**观测口由项目定义**：「真正发出的上报」在哪看、拦截看哪里、业务自己的崩溃收集口在哪，是被测系统的知识。层的名字固定，每层在本项目里指什么写进配置：`acceptkit config add quality.observePoints '{"layer":"report","means":"交给上报 SDK 的那一下"}'`；内核自带的效果词也可以同名替换（改 match / covers，或加 `except` 正则）。用例写了某个效果、项目里却没有任何操作读那一层时，Q22 报的是「项目还没有这个观测口」：用例自己补 —— 回被测系统里查清楚这一层的出口、什么情况下会走到、带哪些字段，写成操作并登记 `--observes`，再回填用例。

同一份判断还用在三处：observe 机判时断言比观测宽就不自己关复核、排进盲审；盲审包列出主张清单，判 ok 要逐条写出在证据哪里；记了 pass 但主张没被覆盖、也没逐条复核过的，算证据缺口（`claims_uncovered`），继承下来的 pass 一样。

**行话清单**：内核带通用的几条（`core/case-quality.mjs` 的 `JARGON`），项目自己的写进配置：`acceptkit config add quality.jargon "<正则>" --say "<改成怎么说>"`。内核和项目私有规则自己的文字也过这份清单（`doctor` 检查，内核的由测试守着）：检查者自己说行话，这道闸就永远不会把它标红。

危险动作的识别可以按项目扩展：在项目配置里写 `"quality": { "dangerOps": "触发|execute" }`（正则）。

## 机器判断不了的：评审时逐条问

- 被测改动不存在时，这条断言还会成立吗？成立就是平凡断言，测不出改动。
- 前提（guard）证明的是「输入真的生效了」，还是只证明了「页面开着 / 环境就绪」？
- 断言读的是下游真正消费的产物，还是记录面、页面回显？
- 开关、配置的取值是运行时读回的真值，还是代码里的默认值？
- 预期出自契约、基线读回，还是谁的裁定？基线版本上同样读回是多少？
- 这一步在产品里有页面 / App 入口吗？有就要走入口，不能用接口代测。
- 判据面在这个环境里观测得到吗？没有对应的观测操作，就在评审时提出，不要执行时拿别的面顶替。

## 项目特有的规则

项目扩展包导出 `qualityRules`，格式与通用规则相同（`id`、`level`、`title`、`why`、`fix`、`check({ c, cfg })`），追加在通用规则之后。适合放某个已淘汰的观测面、某类用例必须带的守卫、只允许操作的租户这类和项目绑定的规则。
