# 用例质量标准

用例是资产：一条用例写坏了，每次执行都会产出坏结论。所以每次新增或修改用例，都按同一套标准检查。规则来自成熟用例库里反复出现的坏写法，每条都写明「教训」，也就是违反它在历史上导致过什么。

规则的正本是 `core/case-quality.mjs`，`acceptkit quality --standard` 打印当前项目实际生效的规则，包括项目扩展追加的规则。

## 什么时候检查

| 时机 | 做什么 |
|---|---|
| `acceptkit new` 新建用例 | 打印标准和自检问题，照着写 |
| `acceptkit validate <case>` | 按规则检查；有不达标项退出码 1 |
| `plan check` / `plan approve` | 评审单里任何一条用例不达标都算硬错，不能批准；同时列出评审时要逐条问的问题 |
| `acceptkit run` | 不达标的用例不能开跑（调查类 probe 用例除外） |
| `acceptkit quality` | 全量盘点：新问题、存量质量债、已豁免 |

## 两档

- **✗ 拦截**：新增或改过的用例不达标，就不能进评审单批准，也不能开跑。
- **⚠ 提示**：列出来，由作者确认。

## 存量用例

引入标准时已经存在的用例，用 `acceptkit doctor --fix` 登记基线。基线里已有的问题记为**质量债**，只提示，不拦截。改过的存量用例只拦**新增**的问题，不会因为改了一个字就把旧债全部变成拦截。新项目（`project init`）的基线是空的，每条用例都按标准拦。

## 例外

个别断言确实要例外时，在断言（或节点、用例）上写明理由：

```json
"quality_waive": [{ "rule": "Q04", "why": "这条是计数为 0 的契约断言，对照在兄弟断言 E3 里" }]
```

豁免会在检查结果里显示为「已豁免：理由」。没写 `why` 的豁免不生效。

## 通用规则

| 规则 | 档 | 坏写法 | 教训 |
|---|---|---|---|
| Q01 断言要有判定方式 | ✗ | 没有 `observe`，只有一句文字判据 | 没有机器判据的断言大多落成「待测」或「阻塞」；判据临场想，两次执行判法不同。确实只能人判，写 `judge: "human"` 和 `human_why` |
| Q02 断言必须可判定 | ✗ | 「启动正常」「有相关输出」、模板占位 | 执行人按自己的理解判，通过了也说明不了什么 |
| Q03 一条断言只判一件事 | ⚠ | 一条断言三个子句，判据只有一条 | 证据只证明了其中一件，复核按「证据不足 / 夸大」驳回 |
| Q04 阴性判定要有前提 | ✗ | 「没出现 / 计数为 0」，没有 guard | 功能根本没跑、开关没生效、数据被淘汰时同样成立，平凡通过 |
| Q05 提交成功不等于生效 | ✗ | 只断言「保存成功」「code=0」，之后没有回读 | 页面提示已保存，重新打开值没变：出过假通过 |
| Q06 危险写操作要结构化标记 | ✗ | 「发布 / 删除 / 清空」只写在操作文字里 | 执行到一半才发现要人确认，整段记阻塞。写 `danger: { kind, confirm }` |
| Q07 全新安装类断言要标卸载 | ⚠ | 断言要求全新安装，没标 `requires_uninstall` | 卸载会清掉登录态，必须单独审批 |
| Q08 依赖的前置状态要写明 | ⚠ | 要求「默认关闭」，没写前置也没有 guard | 上一轮改过状态没复位，下一轮直接阻塞或误判 |
| Q09 用例里不写执行状态 | ✗ | 用例里有 `status` / `blocked_on` / 「当前必红」 | 执行状态属于某一次运行，写进用例会被下一轮当成规格 |
| Q10 不用自造字段 | ⚠ | 切面写成 `classify`、字段拼错 | 工具不认，覆盖统计看不见，静默失效 |
| Q11 对照分支的预期不能一样 | ✗ | 开关两档的分支写着同样的断言 | 两个分支都通过，测不出开关有没有起作用 |
| Q12 主张要逐条有断言支撑 | ⚠ | 主张的 `proved_by` 列了全部断言 | 等于没说哪条证明了它，复核无从下手 |
| Q13 页面判定不读整页文本 | ⚠ | `observe` 读 `document.body.innerText` | 整页文本里有背景页、隐藏层的旧内容 |
| Q14 硬预期值要有出处 | ⚠ | 断言里写死数值，没有 `source` | 分不清是被测错了还是预期写错了 |
| Q15 同平台有多个被测 App 时要写在哪个 App 上跑 | ✗ | 用例没写 `host`，而该平台登记了多个 App | 只在某个 App 上成立的做法、它的包名和构建都取不到；「这个 App 上没有」分不清是被测物还是 App 的特性 |

| Q16 用例正文说人话，不用行话 | ✗ | 标题、为什么、操作、断言里有「臂 A」「两臂」这类要先学才看得懂的词 | 断言是要念给人听的验收结论；括号里已经是人话时，前面的行话只是多余的门槛 |

Q15、Q16 是基线登记之后加的（`since`）：对基线里的存量用例只提示，对新用例照常拦。

**行话清单**：内核带通用的几条（`core/case-quality.mjs` 的 `JARGON`），项目自己的写进配置：`acceptkit config add quality.jargon "<正则>" --say "<改成怎么说>"`。内核和项目私有规则自己的文字也过这份清单（`doctor` 检查，内核的由测试守着）：检查者自己说行话，这道闸就永远不会把它标红。

危险动作的识别可以按项目扩展：在项目配置里写 `"quality": { "dangerOps": "触发|execute" }`（正则）。

## 机器判断不了的：评审时逐条问

- 被测改动不存在时，这条断言还会成立吗？成立就是平凡断言，测不出改动。
- 前提（guard）证明的是「输入真的生效了」，还是只证明了「页面开着 / 环境就绪」？
- 断言读的是下游真正消费的产物，还是记录面、页面回显？
- 开关、配置的取值是运行时读回的真值，还是代码里的默认值？
- 预期出自契约、基线读回，还是谁的裁定？基线版本上同样读回是多少？
- 这一步在产品里有页面 / App 入口吗？有就要走入口，不能用接口代测。
- 判据面在这个环境里观测得到吗？没有对应的观测操作，就在评审时提出，不要执行时拿别的面顶替。

## 项目特有的规则

项目扩展包导出 `qualityRules`，格式与通用规则相同（`id`、`level`、`title`、`why`、`fix`、`check({ c, cfg })`），追加在通用规则之后。适合放某个已淘汰的观测面、某类用例必须带的守卫、只允许操作的租户这类和项目绑定的规则。
