# finding 怎么写，什么时候介入

finding 是写给 owner 拍板用的。读的人没参与执行，只看这一条，就要能做决定。
看不懂的 finding 不会被定对，只会被硬定，或者一直挂着。

## 一条合格的 finding 回答五件事

按 owner 读的顺序排列：

| 字段 | 回答什么 | 反例 |
|---|---|---|
| `--decide` 要你定 | 一句问句。owner 回答它就算定了 | 「两件要定：① … ② 生成器要不要同步修」：② 是执行者自己的活，不该问 |
| `--kind` 性质 | 产品缺陷 / 设计缺陷 / 需求没写清 / 用例或工具的问题 / 环境问题。决定 owner 用什么心态看它 | 没写，owner 分不清是不是 bug |
| `--impact` 影响范围 | 谁会碰到？线上用户受不受影响？面有多大（条数、比例）？ | 放在最后一段，前面全是断言原文 |
| `--why` 为什么 | 读懂这条要知道的**那一件事**，用人话讲 | 「node_mode=3 ALWAYS：恒判真，F 支不可达」：没说为什么一定不命中 |
| `--option` × N + `--recommend` | 每个做法选了会怎样（「不处理」也是一个选项），执行者推荐哪个、为什么 | 只有问题，没有选项和后果 |

代码标识、断言原文、文件路径、实测分布这些**放 `--detail`**。看板把它折叠成「技术细节」，给要核对的人看。
人话区（一句话 / 影响 / 选项 / 推荐）里出现 `字段=值`、`Xxx::Yyy`、文件路径、`**`、`⇒`、全大写常量名，工具都会拒收。

```
acceptkit plan finding DEMO-1 \
  --what "20 条断言测的是一种不可能出现的情况，永远过不了" \
  --kind test_defect \
  --impact "只影响验收本身：通过率被压低了一截；被测行为是对的，线上用户不受影响" \
  --why "这类节点配置成「无条件执行」，「条件不成立」那一支根本不会发生" \
  --option "删掉这 20 条 => 通过率如实；评审单改一版，要你重新批" \
  --option "保留，标不适用 => 留痕，但列表里一直挂着" \
  --option "先不动 => 每轮都记失败，永远不会全绿" \
  --recommend "删掉：它们测不出任何东西" \
  --decide "这 20 条删掉还是标不适用？" \
  --detail "<断言原文、配置字段、实测分布…>"
```

## 什么时候介入

质量问题越晚发现越贵：到了 owner 眼前才发现看不懂，就要多一个来回。所以闸放得越早越好。

| 时机 | 谁 | 做什么 |
|---|---|---|
| **0 · 开 finding 之前** | 执行者 | 自问三句：① 根因查实了吗？没查实就是执行阻塞（`record --status blocked`），不开 finding。② 只有 owner 能定吗？自己能定的不问，在 finding 外直接做。③ 是不是已有一条在讲同一件事？是就改写那条（下一行），不另开。 |
| **1 · 写入时** | 工具 | `plan finding` 检查五件事和人话区。缺一样就拒收，并逐条告诉执行者缺什么。 |
| **2 · 同一件事有了新进展** | 执行者 | `plan finding <D> --finding Fxx …` 改写原条，旧写法自动留在 `prior` 里。**不另开一条**：另开会变成更正链，owner 得自己拼出最新结论。 |
| **3 · 摆给 owner 之前** | 看板 | 不合格的（含存量旧条目）不计入「等你定」，放到裁定页最下面「执行者还没写清楚」。`plan check` 把它们列成执行者的待办。 |
| **4 · owner 读了还是看不懂** | owner | 裁定页点「看不懂，退回重写」，写一句哪里看不懂。这不算拍板，不写 `decided_by`。执行者照那句改写后，这条才回到「等你定」。 |
| **5 · 不用 owner 定了** | 执行者 | `plan settle` 收口（被取代 / 已有答案 / 执行者自己的活），带理由，owner 可推翻。 |

时机 4 是兜底：工具查的人话规则只能挡住明显的几类，漏掉的靠 owner 一键退回。
退回的原话会留在 `bounce_history` 里，以后可以拿来补检查规则。
