## 目标：用盲审模型逐项打分取代关键字判定

**每条用例按 11 个维度逐项打 0–3 分、任一项低于 2 分就不能执行也不能批准评审单，分数由一个没写这条用例的模型（盲审）按工具给的标准和事实来打，工具核对后存进 SQLite 并在 plan / run / report 上起作用。** 改造前由关键字规则直接判「清晰 / 待澄清」，判不了语义。改造前实测漏过：

- 「执行注入计划「X」（文件 probes/x.json）」（注入计划：一份列着要直接交给引擎判定的事件的文件）—— 关键字规则认「执行」加一个「」就算具体，放过。当时（2026-11-26 13:24 之前）它挂的操作登记成了观测类、iOS 上没有人看步骤，人照着做不了；新评审把这两点作为硬事实压到 1 分后，操作才被改成动作类并补了步骤。
- 预期前面只有「打开诊断台」（app 里看引擎决策结果的调试页），看不出是什么操作产生了要看的结果；而看启动时策略有没有装上的预期，一上来就打开诊断台是对的。差别在语义。
- 分组标题（例：「D3 引擎内 emit 生成了第二段事件」）在看板上渲染成「步骤」并挂「注入」标签：当时数据里它只标了「是分组」，规则跳过它，展示却当一步。现在分组是单独的节点类型，看板画成标题、不挂触发标签。

## 原则：代码定上限，模型判分，只认盲审

**工具收事实、给每个维度的标准和分数上限，模型逐项打分并写理由，工具核对复述和上限后才记账、用分数拦执行，过门槛只认没写这条用例的模型做的盲审（`--by blind`），写用例的会话自评只算草稿。** 对应 skill-refactor 方法的 J 原则（`skill-refactor/docs/001-method.md` 第四节：能确定判出的由代码判，值不值得、对不对由模型判）。

1. **硬事实定上限**：形状上能确定判出的才给分数上限 —— 节点没有 op 文本、步骤里塞着 JSON / 空值 / 乱码、挂的操作在本平台没有人看步骤、挂了观测类操作当动作、界面字在被测代码里逐字找过且找不到、触发来源算出 unknown。
2. **软信号必答**：可能误报的（「像结论句」「库里有相似操作」「按第 N 步引用」）不定上限，列成必答项：模型逐条 `accept`（采纳）或 `dismiss`（驳回，引用一条本项范围内的反证事实）。
3. **按维度复述**：模型打分前要把被评对象复述成固定字段（例：能照着做 → `{where, do, input}`），工具逐项核对复述的值确实出现在步骤原文、参数、操作人看步骤或 see 里。编不出来就说明这一步不具体。
4. **只认盲审**：写用例的会话自己打的分只算草稿；过门槛只认 `--by blind`（新上下文的子 agent 只看评审包评）。
5. **批量**：一次对一批用例打包，一次提交 jsonl，逐行收或拒。

| 配置集 | 「跑之前被测端处在什么配置下」的一组项，在 `ops/configs.json`，节点用 `config` 引用；每项可以写用哪个操作施加（`apply`，可选） |

| 评审 / 评审包 / 评审记录 | 评审：给一条用例逐项打分。评审包：工具打包给盲审的材料（事实 + 标准 + 上限 + 必答信号）。评审记录：核对通过后存进 SQLite 的分数 |
| 门槛 | 每项最低 2 分才能执行 |
| 项指纹 | 一个评审项依赖的内容的哈希，变了这一项就过期。动作项：节点本身、展开的操作步骤、操作登记的种类和触发来源、引用的配置集；预期项：从根到它的整条链、预期本身、观测操作的 reads / input / 人看步骤、工具算的触发来源；用例项：树骨架 / 前置条件 / 预期的 role。都带标准版本。界面字查得到没有不进指纹（看板和 next 不搜代码）；被测代码变了让上限掉到已打分数以下时，门槛按「过期」处理 |
| 复述字段 | extract 里每个维度要填的字段：A1 的 where / do / input（where 写 `{app:true}` 表示只写了「在 app 里」），E3 的 map（主张 → 第几条判据）和 same（两者说的是不是一件事），C1 分组的 is_title（是不是只做标题）|

| 分数上限 | 工具按硬事实算出的这一项最多能打几分（cap）；盲审打得比它高，这一行被拒收 |

| doctor | `acceptkit doctor --fix`，把旧格式一次性改成新格式，并打开项目的评审门槛 |
| plan / run | acceptkit 的两步：plan 是需求的评审单（验哪些用例，要 owner 批准），run 是执行一次用例 |

| 事实上限（上限、cap） | 由硬事实算出的这一项最多能给几分；模型打分不能越过 |

## 用例数据结构：节点分动作和分组，预期加因果和角色

**节点分动作和分组两种并带稳定 id（nid），预期新增结构化的因果（because）和角色（role），观测操作登记新增读法（reads），旧数据由 doctor 一次迁移。**

- 迁移由 doctor 一次完成。
- 质量规则 Q39 拒收：还带 `group` 键的节点、带操作的分组、写成字符串的 because、重复的 nid。
- 没写 `kind` 的节点就是动作（字段缺省值）。

节点（都有 nid：用例内唯一、永不复用 —— 删掉的节点的 nid 记进用例的 retired_nids，不再分给新节点；n1.2 这种位置编号只用于显示，clarify 里指定节点的参数两种编号都收）：

| 字段 | 动作 `kind:"action"` | 分组 `kind:"group"` |
|---|---|---|
| op | 必填：在哪 + 做什么 + 输入什么 | 必填：这组验什么（分组标题也写在 op 里，读 op 的代码不用跟着改，靠 kind 区分） |
| op_id / params / input | 可选 | 禁止（Q39 拦；`clarify --kind group` 也拒） |
| config | 可选 | 可选（按配置分支组织） |
| children / expect | 可选 | 至少有一样 |

预期新增 / 改动的字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| because | `{ from: "step", step: <nid>, input, why }` / `{ from: "state", why }` / `{ from: "artifact", why }` | 结果从哪来。step：链上哪一步的什么输入产生它 —— `clarify --because-from step` 写入时就核对 step 是这条预期链上的动作、input 是那一步文字 / 参数 / 操作步骤里的字；state：验启动 / 配置后的状态；artifact：静态产物检查 |
| role | `"claim"`（缺省）\| `"control"` \| `"precondition"` | 验需求本身 / 对照 / 前置检查。取代 assert 里手写的「★」 |
| demand_ref | 字符串，可选 | role=claim 时指向评审单改动面 |

其余新增的写法：

| 写什么 | 怎么写 | 为什么 |
|---|---|---|
| 步骤自己的触发来源 | `clarify --node <nX> --input real\|mock-global\|injected --why …` | 注入由观测操作代做时，界面上没有输入入口，要在步骤上说清 |
| 前置条件 | `preconditions: [{ text, op_id? \| manual: { why } }]`；`clarify --precondition-set <序号\|new> --text … --how op:<操作>\|manual --why …`、`--precondition-rm <序号> --why …`，改前留底 | 每条前置要么有操作能建立，要么写明人工确认的理由 |
| 观测读的是什么 | 操作登记 `reads: per-event \| startup-state \| config \| artifact`（`ops set <op> --reads …`） | 读逐事件结果的预期，前面必须有产生事件的动作 |
| 步骤真实产生的值 | 执行时 `record <run> --step <nX> --capture room_id=…`；判据写 `{step.<nX 或 nid>.room_id}`，没记就观测不了 | 真实操作每次产生的 id 不一样，判据写死一定对不上 |

## 评审维度与门槛：11 个维度，每项不低于 2 分才算过

**11 个维度每项 0–3 分，任一项 < 2 用例就评审未过，分数只认没写这条用例的模型盲审，形状规则只定上限，语义交给模型，可能误报的只做模型可驳回的软信号。** 门槛 2 的含义：在哪、做什么、输入什么都有，只缺手势、等待、文案这类不改变路径的细节；1 = 要猜在哪一页、做什么或输入什么。

- 例外：role=control 的预期，E2 / E3 为 1 只警告。
- 跑过之后 A1 / E2 还是 2 分的项算「跑过了还是 2 分」，要补到 3 或判不可执行。

| 维度 | 人话名 | 对象 | 复述字段（extract，工具核对） | 硬事实上限 | 软信号（必答） |
|---|---|---|---|---|---|
| A1 | 能照着做 | 动作 | `{where \| {app:true}, do, input \| {none,why}}`，每项是步骤文字 / 参数 / 操作人看步骤 / 配置集项里的字 | 没有 op 文本也没有 op_id、步骤里塞 JSON / 空值 / 乱码 → 0；引用的操作不存在、挂了观测类操作、操作本平台无人看步骤、界面字逐字找不到 → 1；界面字查不了（没登记被测仓或搜索出错）→ 2 | 没有「动作 + 界面字」的形状；「」里像文件名 / 路径 / id；有子步骤没预期、自己没动作的节点可能是分组 |
| A2 | 该不该是操作集 | 动作 | `{decision: "ref:<操作>" \| "new-op" \| "inline", why}`；ref 的操作要存在、不是观测类、本平台有人看步骤 | 引用的操作不存在 / 是观测类 / 无人看步骤 → 1；没挂操作、同一段文字在别的用例也有 → 1 | 库里有相似操作；步骤里直接写着命令 |
| A3 | 触发说清了 | 动作 | `{from, why}`，from 不能比工具算的更好 | unknown → 1；injected 没有理由 → 0 | — |
| A4 | 一步一事 | 动作 | `{actions: [...]}`，每项是步骤原文里的字；数出 2 个最多 2 分，3 个以上最多 1 分 | — | 步骤里描述了配置 / mock 却没挂配置集；一步里有条件分支 |
| A5 | 可复现 | 动作 | `{deps: [...]}`（没有写 `[]`） | — | 依赖自然发生的事件或等待；按「第 N 步」引用别的步骤 |
| E1 | 结果由哪步产生 | 预期 | `{because}`：原样复述用例里的 because | 没写 because、because.step 不在链上、观测读逐事件结果而前面没有动作、because 说验状态而观测读逐事件结果 → 0；because.input 不是那一步里的字 → 1；观测操作没登记 reads → 2 | 验状态的预期挂在动作下面；观测读启动后状态，because 却说某一步产生 |
| E2 | 照着看得出 | 预期 | `{page, row, pass_when}`，每项是 see 或观测操作人看步骤（填好参数）里的字 | see 空且观测操作无人看步骤、see 里有乱码 → 0 | 说了进某页，没说怎么进 |
| E3 | 判据对得上 | 预期 | `{map: [{claim, check \| null}], same}`：assert 里的主张对应第几条 check，没有判据写 null（有 null 最多 2 分） | 没有判据 → 0；观测读真实事件、这条预期链上却是注入 → 1 | 判据写死了某一次的读数；判据写死长 id（该用 `{step.…}`）；assert 里用「★」 |
| C1 | 结构 | 每个分组和整条用例 | 分组 `{is_title}`，用例 `{issues: [...]}` | 空分组、没有预期也没有下一步的动作 → 0；分组挂着操作 / 参数 → 1 | 分组标题像动作 |
| C2 | 前置可建立 | 用例 | `{pre: [{how: "op:<id>" \| "manual", why}], missing: [...]}`，pre 和前置一一对应，missing 列步骤里用到却没登记的前提（有内容最多 1 分） | 前置只有一句话、没写怎么建立 → 1；引用的操作不存在 → 1 | — |
| R1 | 验到需求 | 用例 | `{map: [{surface, expect \| null}]}`，expect 要是 role=claim 的预期；没有预期在验的改动面写 null（有 null 最多 1 分） | 没有 role=claim 的预期 → 0 | — |

每条 < 3 的项要写 fix：一条改用例（clarify 本用例）、改操作库（ops set）或改配置集（configset set）的命令；工具核对前缀和用例名，把用例名当配置集名的会拒收。

## 评审包、提交、评审记录：assess 打包，jsonl 提交，逐行核对后进 SQLite

**命令都挂在已有的 assess 下（`--pack` 打包、`--apply` 提交、`--status` 看状态），提交的 jsonl 逐行按下文的核对收或拒，收下的记录进 SQLite。** 最初设计的单独 review 命令和目录，和已有的「复核一次执行」命令、盲审队列目录撞名，弃用。

| 命令 | 做什么 |
|---|---|
| `acceptkit assess --pack [--plan D \| --case a,b] [--changed] [--limit N] --json` | 输出评审包；`--changed` 只打包没盲审过或指纹变了的项 |
| `acceptkit assess --apply <文件.jsonl> --by blind\|self --json` | 一行一个评审项，逐行回收下或拒收（拒收带一句能照着改的话） |
| `acceptkit assess --status [--plan D \| --case a,b] [--json]` | 每条用例的状态（通过 / 未过 / 过期 / 只有自评 / 不完整）和低于门槛的项 |
| `acceptkit assess --walk [--plan D \| --case a,b]` | 逐节点走查视图 |
| `acceptkit assess --walk-done <用例> --by <人> --seen <全部节点和预期 id> --notes …` | 走查签收 |

评审包：

| 字段 | 含义 |
|---|---|
| card | 包号；提交时每行带回 |
| rubric | 维度 → `{ name, question, levels{0,1,2,3}, restate }`（`case-review.mjs` 的 `DIMS`） |
| cases[].facts[] | `{ id, at, type, text, hard? }`：at 是 nid / 预期 id / case；hard 是 `{dim, max}`，表示这条事实定的上限 |
| cases[].signals[] | `{ id, at, dim, type, text }` |
| cases[].items[] | `{ key, dim, at, pos, cap, cap_facts[], signals[], fp }`：key = `case:<用例>\|<维度>\|<nid 或预期 id 或 case>`；fp 是项指纹 |

包里掺 2 道考题：项目登记的原题优先（`assess --canary-add "<步骤原文>" --max <最多几分> --quote "<owner 原话>"` 登记进 review_canaries），不够 2 道用内置的通用原题补。考题按哈希插在第一条用例评审项列表里的某个位置（可能在动作、预期或用例级项之间），位置编号是新的顶层编号，形状和真的动作项一样（位置编号、16 位指纹、f 开头的事实编号、触发来源事实、A1–A5 五项），哪几项是考题只记在 review_cards.canaries 里；A1 打得高过它的上限整批拒收；考题的 A2–A5 收下但不存进评审记录（它们只是让考题看起来像真的动作项）。

提交（jsonl，每行一项）：`{ card, key, fp, score, extract, rulings: [{signal, ruling, why, evidence[]}], reason, evidence[], fix }`。

核对（任一不过 → 这一行拒收）：

1. card 存在，fp 等于出包时的指纹，也等于现在的指纹（不等 → 「先重新打包」）。
2. score 是 0–3 整数且 ≤ cap。
3. reason 非空；evidence 至少一个，都是本项范围内的事实（同一 at、at=case，预期还可以引用链上各步的事实）。打包时给 E1 项补的「because 指向那一步当前的 A1 盲审分」也算本项事实：打包和收分用同一份补法，不然盲审引用它会被错拒。
4. 每个 signal 都有 ruling；dismiss 要写 why 并引用一条本项范围内的事实。
5. score < 3 时 fix 符合上面的前缀规则。
6. extract 按维度核对（见上表）。
7. 考题打得高过它的上限 → 这张包整批拒收。
8. 跨项一致：E1 ≥ 2 且 because 指向某一步时，那一步的 A1（本次提交或已有盲审记录）必须已评且 ≥ 2。

存储（SQLite `core/store/db.mjs`，schema 升到 3，只加不删）：

| 表 | 字段 |
|---|---|
| assessment_items（已有，加列） | score, cap, item_fp, facts, extract, rulings, card_id, reason |
| review_cards（新） | id, at, demand, cases, rubric_version, extractor_version, items（key → 指纹）, canaries |
| review_canaries（新） | id, dim, item, max_score, source, quote |

一次 apply 里每条用例 = assessments 一行（phase=review，by=blind/self，不互相取代），每个收下的评审项 = assessment_items 一行；状态按 key 取最新的盲审 / 自评记录现算，不存「过期」这种派生字段。因为按「最新一次提交」生效，晚出的包已经给某项打过分时，早出的包再交上来的这一项拒收，免得把新分盖回旧分（多轮盲审补交、重放旧结果时会发生）。不做哈希链：没有密钥的链，有 shell 权限的 agent 能整条重算。

## 门槛接在哪：批准评审单、开跑、出报告三处

**门槛接在三处，批准评审单时不满足就不批并列出哪项和 fix，开跑时不满足就拦下（跳过评审单检查的开关也绕不过），出报告时如果开跑时评审没过、判定从 PASS 降为 PARTIAL 并把原因写进判定备注，都只在项目接入后生效。**

| 位置 | 不满足时 | 落在哪 |
|---|---|---|
| 接入 | doctor --fix 打开后每条用例都拦，不按新旧豁免；没接入只提示、不出评审提醒卡片 | SQLite meta 的 review_gate_since |
| 批准评审单（`plan approve`） | 不批，列出哪条哪项和 fix | `planAssessGate` |
| 开跑（`run`） | 拦下，提示打包盲审；`--skip-plan-gate` 绕不过；probe 类用例只要求 A1、E2 | 开跑时的状态写进 result.json 的 review |
| 出报告（`report`） | 开跑时评审不是「通过」→ PASS 降为 PARTIAL | result.json 的 verdict_notes |
| 走查签收 | 没签收或签收后用例又改过 → 批准和开跑都拦（smoke 类用例不查） | SQLite meta 的 walk:<用例> |
| 卡片（`next`） | 出评审提醒卡片（没评 / 过期 / 只有自评 / 低于门槛）和复评卡片（跑过后 A1 / E2 还是 2 分，附那次实际做了什么） | `core/next.mjs` |

逐节点走查签收和盲审分工不同：盲审逐项打分管「每一项够不够格」，走查管「整条连起来有没有人看过、说得通」。走查视图按树的顺序列出每一步和每条预期（人话、操作展开、因果、see、判据、分数和低分理由）；签收要列出全部节点和预期 id，缺一个拒收，记下签收时的用例指纹，用例之后再改签收就作废。

- 看板：用例一个评审标签；点开只列低于门槛和「跑过还是 2 分」的项（人话维度名、分数、理由、fix），2 分的项另计「待跑后补准」。分组渲染成标题，不带触发标签。

## 和现有规则的关系：评审是新加的一层，现有规则照旧跑

**评审是新加的一层，现有规则照旧跑，它们的判据被搬成了评审的事实和信号。**

- `core/assess.mjs` 的事前评价（rubric 1，0–5 加权）和它的卡口照旧，评审记录用自己的 phase=review，不混。
- clarity 的形状规则（JSON 进步骤、空值、命令、导航、界面字核对）在评审里重新实现成 A1 / A2 / E2 的硬事实或信号；clarify 命令自己的提示仍用 clarity。
- case-quality 的 Q31–Q38 照旧作为质量规则运行（Q31、Q32、Q34、Q37 是 block），评审不引用它们，但 A3、E3 用同一份触发来源推算。
- 界面字三态 found / missing / unknown 只用在评审路径：没登记被测仓、搜代码出错都算 unknown，出错不写缓存。
- `clarify --group` 改为 `clarify --kind action|group`。

## 迁移（`acceptkit doctor --fix`，一次完成、可重复执行）

**迁移由 `acceptkit doctor --fix` 一次完成，先备份，再改写节点形状、分配 nid，不替存量猜 because（由作者逐条补，补之前 E1 上限 0），最后写 review_gate_since 打开评审门槛。** 没接入的项目只提示、next 不出评审提醒卡片。

1. 改写前的用例文件复制到项目 `attic/cases-before-nodes-<日期>/`。
2. `group: true` → `kind: "group"`，标题文字仍在 op。像分组却没标记的节点不替它们改，评审时由信号提示。
3. 每个节点分配 nid；已有字符串 `id` 字段的节点改名 nid。
4. 不补 because：缺的由作者逐条补（E1 上限 0）。
5. 评审单底稿（`state/plans/*.snap`）同样改写；钉住的用例指纹：改写前等于钉的值的，按改写后的文件重钉（仍是文件内容的 sha256），改写前就已被改过的保持「已改」。
6. 写 review_gate_since，打开评审门槛。

## 还没做：5 条，影响最大的是改了触发来源不作废旧结论

**设计上要、代码里还没有的 5 条，影响最大的是：步骤的触发来源改了（注入 ↔ 真实），旧的执行结论不会自动作废，只能靠 recheck 时人看。**

| 项 | 现状 | 影响 |
|---|---|---|
| 触发来源改前改后不同 → 按「判法改了」作废旧结论 | `classifyCaseEdit` 不比触发来源 | 把步骤从注入改成真实（或反过来）后，旧的执行结论不会自动作废，靠 recheck 时人看 |
| 看板标出「驳回了软信号」的项 | 看板不读 rulings | owner 看不到盲审驳回了哪些工具提示 |
| 标准里的正反例取自项目 lessons / owner 驳回原题 | rubric 只有工具内置的 levels；owner 驳回的原题可登记成考题（`assess --canary-add`），但不进 rubric 正反例 | 盲审看不到项目特有的坏写法长什么样，只在考题上被抽查 |
| fix 完整 dry-run（节点在、参数名对） | 只核对前缀和用例名 | 盲审写错的 fix 要执行时才发现 |
| doctor 报出含乱码（U+FFFD）的用例 | 只在评审里作为硬事实（上限 0） | 不打包就看不到 |

## 风险：盲审打分偏松、形状规则误伤

**主要风险是盲审打分偏松和形状规则误伤，应对是分数不能越过硬事实给的上限、复述编不出原文就拒收、考题打得高过它的上限整批拒收、形状规则只定上限而语义交给模型。**

| 风险 | 后果 | 处理 |
|---|---|---|
| 盲审给分偏松 | 含糊用例混过 | 硬上限不能越；复述编不出就过不了；考题打得高过它的上限整批拒收 |
| 形状规则误伤 | 好用例被拦 | 硬上限只用确定的形状（JSON、空值、乱码、操作不存在 / 无人看步骤、界面字逐字找不到）；可能误报的只做软信号，模型可驳回 |
| 上线即拦 | 在跑的需求全红 | 门槛按项目接入；next 出评审提醒卡片驱动补评；`--changed` 只评没评过 / 过期的 |
| 迁移打断批准 | 钉住的用例指纹全显示「被改过」 | doctor 对改写前未改过的按改写后内容重钉（实测 103 个重钉、133 个保持「已改」） |
| 有 shell 权限的 agent 直接改库 | 分数被篡改 | H2 钩子挡住用写文件工具改库；挡不住 shell，如实承认 |
